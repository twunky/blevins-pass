## File cleanup and organization

Do this as a separate maintenance proposal, not a closeout mass move. Keep Phase1 and Phase2 provenance intact.

1. Establish one current onboarding README and one current Phase2 handoff; label old prompts/reviews as history. Prefer links over duplicating status paragraphs.
2. Index verification scripts/evidence by scenario, command, data fixture and cutoff. Recover the worker's scratch-only partial-sellout browser script if available; do not reconstruct it and label it original.
3. Propose a dedicated verification-tool folder for standalone audit/probe projects, updating documented paths and commands together. Keep meaningful independent probes distinct from normal server tests; promote useful regressions deliberately.
4. Preserve requirement images, native/raw transcripts, filenames/hashes and redaction provenance. Review generated build outputs and SQLite backups for private data; do not broadly delete or relocate owner files. Existing bin/obj outputs are ignored; do not blanket-ignore session archives.
5. Generate a submission inventory/hash manifest after final exports are captured. Maintain separate original/private and redacted submission copies where necessary, without putting secrets into either new archive.

## Architecture guardrails

Keep the focused .NET API and existing frontend until evidence justifies change. Distributed caches must not become an accidental inventory authority. Do not add microservices, brokers, Kubernetes, WebSockets or another mutable frontend store simply to tick a checklist. A customer ticket waitlist is distinct from traffic admission control. Authentication, production admin, deployment and provider changes require separate scope/security/operational decisions; none was performed during this phase.
